# pr01 — Пользователи, группы, права доступа в Linux

## Цель
Создать второго пользователя и группу, настроить общий каталог с групповыми
правами доступа, проверить и объяснить поведение прав при удалении чужого
файла, объяснить разницу между su и sudo и причину блокировки root-логина,
настроить постоянные alias и переменную окружения в ~/.bashrc.

## Окружение
Ubuntu 24.04.5 LTS (ARM64) в VirtualBox на MacBook (Apple M1).

## 1. Пользователь student2 и группа developers

```
$ sudo groupadd developers
$ sudo useradd -m -s /bin/bash -G developers student2
$ sudo passwd student2
$ id student2
uid=1001(student2) gid=1002(student2) groups=1002(student2),1001(developers)
```

## 2. Каталог /srv/shared

```
$ sudo mkdir /srv/shared
$ sudo chown root:developers /srv/shared
$ sudo chmod 2775 /srv/shared
$ ls -ld /srv/shared
drwxrwsr-x 2 root developers 4096 Sep 23 04:20 /srv/shared
```

Владелец и группа — rwx, остальные — r-x (могут заходить и читать, но не
писать). Setgid-бит (первая цифра «2») делает так, что новые файлы внутри
каталога автоматически получают группу developers, а не группу того, кто их
создал.

## 3. Удаление чужого файла

От имени student2 создан файл в /srv/shared, от имени основного пользователя
(ibro) предпринята попытка его удалить:

```
$ su - student2
$ echo test > /srv/shared/testfile.txt
$ exit
$ rm /srv/shared/testfile.txt
rm: remove write-protected regular file '/srv/shared/testfile2.txt'? 
```

**Объяснение:** право на удаление файла в Unix определяется правами на
каталог, а не правами на сам файл. У /srv/shared право записи есть только у
владельца (root) и группы developers. Пользователь ibro не входит в группу
developers, поэтому относится к категории «остальные» с правами только r-x —
может зайти и посмотреть содержимое, но не может ни создать, ни удалить файл
внутри, даже если тот принадлежит другому обычному пользователю. Удалить его
смог бы root (например, через sudo rm) или любой другой член группы
developers.

## 4. su vs sudo

`su` переключает текущую сессию целиком на другого пользователя (по
умолчанию — root). Требует пароль **целевого** пользователя. После su все
команды до exit выполняются от нового пользователя без разбора, кто и что
именно сделал.

`sudo` выполняет **одну конкретную команду** с правами другого пользователя
(обычно root), не меняя сессию. Требует пароль **своего** аккаунта, а не
root, и работает только если пользователь есть в /etc/sudoers (или в группе
sudo). Каждый вызов логируется в /var/log/auth.log — видно, кто, когда и
какую команду выполнил.

## Почему root по умолчанию не может залогиниться

В Ubuntu у root нет пароля (аккаунт заблокирован), поэтому прямой логин под
root невозможен. Это сделано, чтобы:
- все административные действия были привязаны к конкретному пользователю
  (аудит через sudo-логи, а не анонимный root);
- уменьшить поверхность атаки — нет root-пароля, который можно подобрать или
  украсть;
- приучить работать в обычном режиме с ограниченными правами, повышая их
  только на момент реальной необходимости (принцип наименьших привилегий).

## 5. ~/.bashrc: alias и переменная окружения

Добавлено в конец ~/.bashrc:
```
alias ll='ls -la'
alias update='sudo apt update && sudo apt upgrade -y'
export COURSE_ENV="pr-lab"
```

## Выводы
Права доступа в Linux определяются на уровне каталога (для операций
создания/удаления файлов) и на уровне самого файла (для чтения/записи его
содержимого) отдельно — это разные вещи. sudo безопаснее su, так как не
требует раскрытия root-пароля и логирует каждое действие отдельно. Настройки
в ~/.bashrc применяются один раз к файлу и затем действуют во всех новых
сессиях автоматически.
